# Decision 0053: DPoP proofs are checked against nonces Hodor derives from a secret of the tenant, remembered by their `jti` while they live, and bind access tokens and the refresh tokens of public clients

Status: Proposed (requested by the project owner, who asked for every OpenID certification profile)

## Context

[OAuth 2.0 Demonstrating Proof of Possession (DPoP), RFC 9449](https://www.rfc-editor.org/rfc/rfc9449), binds a token to a key the client holds: every request carries a `DPoP` header, a JSON Web Token signed with that key, naming the method, the address, the time and, at a resource, the hash of the token. FAPI 2.0 requires tokens to be bound to their client, by DPoP or by mutual TLS ([RFC 8705](https://www.rfc-editor.org/rfc/rfc8705)), and its plans in the [OpenID conformance suite](../operations/conformance.md) run once with each. Requirement-OAuth-13 asks for DPoP, and the [threat model](../security/threat-model.md#oauth-2x) names proof replay as Threat-OAuth-15, controlled by a `jti` cache and a nonce from the server.

[Milestone 10](../product/epics.md#milestone-10-workloads-prove-who-they-are-with-their-certificates) binds tokens to certificates with `cnf` and `x5t#S256`, checked wherever Hodor checks a token. DPoP binds them with `cnf` and `jkt`, the thumbprint of the client's key ([RFC 7638](https://www.rfc-editor.org/rfc/rfc7638)), and is checked in the same places.

Hodor runs on several nodes without affinity (Requirement-Performance-07), with Redis optional ([Decision 0007](0007-postgres-required-redis-optional.md)). A nonce every node accepts, and a record of proofs every node sees, must fit that.

## Decision

### What is checked in a proof

- A compact JSON Web Signature of at most 4 kibibytes, `typ` `dpop+jwt`, `alg` `ES256`, `PS256`, `RS256`, and `ES384` and `EdDSA` once the kernel checks them; never `none` or a shared-secret algorithm. The public key is in the header's `jwk`, without a private part.
- `htm` and `htu` are the request's method and address, the address compared without its query and fragment, built from `HODOR_PUBLIC_URL` and never from the request's `Host`.
- `iat` within 60 seconds of Hodor's clock, either way.
- `jti` of at most 64 characters, not seen before for this key within the proof's life.
- `ath`, at a resource, the hash of the access token presented.
- `nonce`, when the tenant or the client requires one, a nonce Hodor gave.

### Nonces derived from a secret, not stored

- A nonce is the HMAC with SHA-256, under a secret of the tenant kept sealed as other secrets are ([secrets at rest](../security/secrets-at-rest.md)), of the current five-minute window, written in base64url. Every node derives the same nonce without asking anyone, and accepts the current and the previous window.
- A request that needs a nonce and has none, or an old one, is answered `use_dpop_nonce` with a `DPoP-Nonce` header, as RFC 9449 says; every successful answer carries the next nonce when the window is about to change.
- Requiring a nonce is the tenant's choice, and a client held to a [security profile](0052-security-profiles.md) that asks for it always gets one.

### Proofs remembered by their `jti`

- A proof's `jti` is remembered with the thumbprint of its key until the proof can no longer be accepted, two minutes, in PostgreSQL in a table under row-level security with an index on expiry, or in Redis when it is there. The worker removes what has expired, as it removes other expired rows.
- Two requests with the same `jti` at once cannot both pass: the record is one conditional insert.

### What is bound

- **An access token** issued with a proof carries `cnf` with `jkt` and `token_type` `DPoP`. It is refused without a proof of that key, or presented as `Bearer`, wherever Hodor checks a token: UserInfo, introspection, the Authorization API and the administration interface. Introspection answers `cnf`.
- **The refresh tokens of a public client** are bound to the key of the first proof; a refresh with another key is refused. A confidential client's refresh tokens are bound by its authentication instead, as RFC 9449 allows.
- **The authorization code** is bound to a key when the request carries `dpop_jkt`, or when it was pushed with a proof ([Decision 0045](0045-request-objects-and-pushed-requests.md)); the code is then redeemed only with a proof of that key.
- **A client may require DPoP** (`dpop_bound_access_tokens` of RFC 9449), and a client held to a profile that asks for it always does.

## Consequences

- FAPI 2.0's plans can run with DPoP, and a public client, a single-page application or a mobile application, gets tokens that are worthless when stolen without its key.
- Nonces cost no storage and no coordination between nodes. A secret of the tenant that leaks lets someone compute nonces ahead, which only weakens the protection a nonce adds on top of the `jti` and `iat` checks.
- Every proof costs a signature check and one row for two minutes. The worker's removal keeps the table small, and Redis takes it off PostgreSQL where it is there.
- Discovery names `dpop_signing_alg_values_supported`.

## Alternatives considered

- **Nonces stored per client.** Each could be used once. Set aside: every node would read and write them on every request, and RFC 9449 does not require a nonce to be used once.
- **No `jti` record, only a short `iat` window.** Cheaper. Set aside: a proof seen once could be replayed within the window, which is what Threat-OAuth-15 is about.
- **Binding the refresh tokens of confidential clients too.** Stricter. Set aside: their authentication already binds them, and a client that changes its key would lose every family.
