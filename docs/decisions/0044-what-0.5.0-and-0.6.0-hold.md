# Decision 0044: OpenID certification is two versions: 0.5.0 holds every OpenID Connect profile, 0.6.0 holds FAPI 1.0 Advanced, FAPI 2.0 and FAPI-CIBA

Status: Proposed (requested by the project owner)

## Context

After the plan of 0.4.0 the project owner asked for every feature that OpenID certification requires to be planned: "plan all the missing features that OpenID Connect certification requires; I want this product to be as complete as possible."

Hodor runs five plans of the [OpenID conformance suite](../operations/conformance.md) on every pull request: Basic, Config and Back-Channel, and Basic and Back-Channel again with pairwise clients. It has never been certified. What it lacks was found by reading the suite's plans at release 5.3.5, of 2026-11-24, and the Foundation's instruction pages; [the target](../operations/conformance.md#the-target) lists, profile by profile, what each requires and where Hodor stands.

The OpenID Foundation certifies these profiles for an OpenID Provider or authorization server today:

| Programme | Profiles | Fee for a member, a non-member ([fees](https://openid.net/certification/fees/)) |
|---|---|---|
| OpenID Connect | Basic, Implicit, Hybrid, Config, Dynamic, Form Post, 3rd Party-Init; RP-Initiated, Session, Front-Channel and Back-Channel logout | US$700, US$3,500 |
| FAPI 1 | FAPI 1.0 Advanced, with `private_key_jwt` or mutual TLS, by value or pushed, plain or JARM | US$1,000, US$5,000 |
| FAPI 2 | FAPI 2.0 Security Profile and Message Signing, with DPoP or mutual TLS | US$1,000, US$5,000 |
| FAPI-CIBA | Poll and ping, with `private_key_jwt` or mutual TLS | US$1,000, US$5,000 |
| OpenID for Verifiable Credential Issuance and for Verifiable Presentations | Issuers, wallets and verifiers, with the High Assurance Interoperability Profile | US$700, US$3,500 |

The suite also has plans for OpenID Connect for Identity Assurance, OpenID Federation and the Shared Signals Framework, each marked as not part of certification (the last two in an early version), and for AuthZEN policy decision points, marked certifiable but with no fee or listing yet.

Most of what is missing is shared between profiles, and some of it is planned already: request objects and pushed authorization requests (Phase 4), DPoP (Phase 4, Requirement-OAuth-13), dynamic client registration (Requirement-OAuth-19), front-channel logout and session management (Requirement-OAuth-20). Mutual TLS client authentication and certificate-bound tokens are planned in [Milestone 10](../product/epics.md#milestone-10-workloads-prove-who-they-are-with-their-certificates) of 0.4.0 (Issues 107 and 108).

## Decision

### Two versions, because the profiles fall in two groups

- **0.5.0 holds every OpenID Connect profile**: the seven OpenID Provider profiles and the four logout profiles, in four milestones:
  1. [Milestone 13](../product/epics.md#milestone-13-requests-that-say-what-they-need): requests that say what they need: request objects, pushed authorization requests, the `claims` parameter, the person's standard claims, and the parameters of a request completed.
  2. [Milestone 14](../product/epics.md#milestone-14-answers-through-the-browser): answers through the browser: every response type, the `fragment` and `form_post` modes, signed UserInfo answers.
  3. [Milestone 15](../product/epics.md#milestone-15-clients-that-register-themselves): clients that register themselves, with initial access tokens, software statements, the management of a registration, and keys at an address.
  4. [Milestone 16](../product/epics.md#milestone-16-sign-out-and-session-state-through-the-browser-and-the-openid-connect-certification): sign-out and session state through the browser, every plan in continuous integration, and the certification of 0.5.0.
- **0.6.0 holds FAPI and client-initiated backchannel authentication**, in three milestones:
  1. [Milestone 17](../product/epics.md#milestone-17-fapi-20-security-profile): FAPI 2.0 Security Profile: DPoP, security profiles per client, mutual TLS for clients that are not workloads.
  2. [Milestone 18](../product/epics.md#milestone-18-fapi-20-message-signing-and-fapi-10-advanced): FAPI 2.0 Message Signing and FAPI 1.0 Advanced: JARM, JWT introspection responses, the hybrid flow under FAPI 1.0, and encryption.
  3. [Milestone 19](../product/epics.md#milestone-19-client-initiated-backchannel-authentication): client-initiated backchannel authentication and FAPI-CIBA, and the certification of 0.6.0.
- **Why two.** The OpenID Connect profiles stand on nothing of 0.4.0, are what most relying parties need, and are certified as one batch under one fee or one waiver. FAPI and backchannel authentication stand on mutual TLS from 0.4.0 and on everything 0.5.0 builds, serve fewer and stricter tenants, and are separate programmes with their own fees. One version would hold seven milestones, about forty issues, and nothing would be certified until all were done.
- **The order follows what each part needs, and its value.** Requests come first because every later profile reads them: response types put claims in the ID token as Milestone 13 decides, registration registers what Milestones 13 and 14 support, and FAPI requires request objects and pushed requests. The browser's logout comes last in 0.5.0 because it depends on response types, every one of which the logout profiles are run with. In 0.6.0, the FAPI 2.0 Security Profile comes first because Message Signing is built on it, and backchannel authentication last because it needs the profiles' request objects and bound tokens.

### The design choices

| Decision | What it settles |
|---|---|
| [0045](0045-request-objects-and-pushed-requests.md) | Request objects and pushed requests become the same pending request, per tenant, by the hash of their reference, used once |
| [0046](0046-responses-through-the-browser.md) | Every response type and mode is offered per client; an access token through the browser only for a client an administrator marks so |
| [0047](0047-claims-and-the-person-s-claims.md) | The `claims` parameter never widens consent; a person keeps the standard claims |
| [0048](0048-encryption.md) | JSON Web Encryption with Hodor's own code over `aws-lc-rs`, a short list of algorithms, encryption keys per tenant |
| [0049](0049-dynamic-client-registration.md) | Registration is off per tenant until an administrator chooses initial access tokens, software statements or open registration, under a policy |
| [0050](0050-logout-and-session-state-in-the-browser.md) | Front-channel logout is a page of Hodor's; session management reads a browser state that is not the session |
| [0051](0051-conformance-runs-and-certification.md) | Which plans run when, and how and when certification is asked for |
| [0052](0052-security-profiles.md) | Security profiles per client; no rotation of refresh tokens under FAPI 2.0 |
| [0053](0053-dpop.md) | DPoP nonces derived from a secret of the tenant, proofs remembered by `jti` |
| [0054](0054-backchannel-authentication.md) | How a backchannel authentication request reaches the person and is approved |

### What is in and what is out

- **In, pulled forward from Phase 4**: request objects and pushed requests (Requirement-OAuth-12), DPoP (Requirement-OAuth-13) and dynamic client registration (Requirement-OAuth-19). **From Phase 6**: front-channel logout and session management (Requirement-OAuth-20). **From Phase 1**: the standard claims of a person (Requirement-Identity-04).
- **Reused from 0.4.0, not planned again**: mutual TLS client authentication and certificate-bound tokens (Issues 107 and 108). Milestone 17 adds only what a client that is not a workload needs: the tenant's own authorities, the subject names of RFC 8705, self-signed certificates and endpoint aliases.
- **Out, with the reason:**
  - *OpenID Connect for Identity Assurance.* Not part of certification, and it needs evidence of identity proofing that Hodor does not keep: who checked which document, when, under which trust framework. Hodor is not an identity proofing service. The `claims` parameter it needs is built, so `verified_claims` from an outside proofing provider can follow if a tenant asks.
  - *OpenID Federation.* Its plans are an early version and not part of certification. Hodor's tenants could each be an entity of a federation, and the decision is left until the Foundation certifies it.
  - *OpenID for Verifiable Credential Issuance and for Verifiable Presentations.* Certified, but for credential issuers, wallets and verifiers, not OpenID Providers: issuing credentials to wallets in the formats they hold, with client attestation, is a product of its own. Left to a later decision of the owner.
  - *The Shared Signals Framework, as a transmitter.* The Foundation's page says it is certified, the suite says it is not, and there is neither a fee nor a listing. The [competitive analysis](../product/competitive-analysis.md#gaps-to-decide-on) already names it as a gap to decide on; it waits for the Foundation.
  - *AuthZEN, for the Authorization API.* Not a profile of an OpenID Provider, but Hodor is a policy decision point, and its plans are marked certifiable. It deserves a plan of its own, which the owner may ask for.
  - *The ecosystems' profiles of FAPI* (open banking in the United Kingdom, Brazil, Australia, Saudi Arabia, the United Arab Emirates and Chile, ConnectID). Each adds rules and endpoints of its own country. The generic profiles come first; an ecosystem is planned when a tenant needs one.
  - *Grant management and rich authorization requests under FAPI 2.0*, which certify as additions to the profile. Rich authorization requests keep Phase 5 (Requirement-OAuth-18), grant management is not planned.
  - *`client_secret_jwt` and ID tokens signed with a client's secret.* No plan requires them, and Hodor keeps secrets only as hashes, so it cannot check a signature made with one.
  - *HTTP message signatures* (RFC 9421) for resources: the final FAPI 2.0 Message Signing does not name them and the suite does not test them.
- **The rules of the project stay.** The documentation of each issue comes first. The cross-tenant suite covers every new reference, registration, token, browser state and request. Each milestone ends with the conformance plans it brings passing in continuous integration against the image, and with a demonstration.
- **Releases.** 0.5.0 is released when Milestone 16 is done, and 0.6.0 when Milestone 19 is done, following [the release rules](../development/conventions.md#releases). Requirement-OAuth-28, encryption, is Optional: if it slips, 0.6.0 is released without it.

## Consequences

- At 0.5.0 Hodor can be certified for every OpenID Connect and logout profile, as Keycloak, Authlete and node-oidc-provider are; at 0.6.0, for the FAPI profiles and FAPI-CIBA, which only some of them hold ([the competitive analysis](../product/competitive-analysis.md#27-openid-certification)).
- The product's rules change in two places, each by a decision: the implicit grant becomes possible for a client an administrator marks ([Decision 0046](0046-responses-through-the-browser.md)), and FAPI 2.0 clients' refresh tokens are not rotated ([Decision 0052](0052-security-profiles.md)).
- Continuous integration runs many more plans, split as [Decision 0051](0051-conformance-runs-and-certification.md) says.
- Certification costs the owner time, a public deployment for a few days, and fees or the waiver. [How certification is obtained](../operations/certification.md) says what is the owner's to do.
- What is left out is not dropped. It keeps its phase, and the roadmap's phases keep their numbers.

## Alternatives considered

- **One version, 0.5.0, with all seven milestones.** One release to plan. Set aside: nothing would be certified until FAPI and backchannel authentication were done, and the OpenID Connect profiles matter to many more tenants.
- **FAPI 2.0 before the OpenID Connect profiles that few use, Implicit and Session among them.** FAPI 2.0 is where the market is moving. Set aside: FAPI 2.0 needs request objects and pushed requests from Milestone 13 anyway, and the OpenID Connect profiles are certified in one batch only once they are all done.
- **Leaving out the Implicit profile, the token types of Hybrid and Session Management**, as practices that RFC 9700 and browsers discourage. Less to build and to defend. Set aside: the owner asked for every profile; each is off by default and behind an administrator's choice.
- **Planning OpenID for Verifiable Credential Issuance too.** It is certified. Set aside for this plan: it makes Hodor a credential issuer, which is a product decision of its own, not a feature of an OpenID Provider.
