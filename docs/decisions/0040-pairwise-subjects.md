# Decision 0040: A pairwise client knows a person by an identifier of its sector alone, in every token, answer and logout it is given

Status: Accepted (made for Issue-98; the project owner asked for pairwise subject identifiers, not for these choices)

## Context

[Milestone 9](../product/epics.md#milestone-9-what-020-left-out) asks for pairwise subject identifiers ([OpenID Connect Core 1.0, section 8](https://openid.net/specs/openid-connect-core-1_0.html#SubjectIDTypes)): a client's subject type, the sector from its redirect addresses or from its sector identifier address, fetched through the guarded outbound client, and UserInfo, introspection and token exchange answering with the same identifier. Two clients of different sectors must get different identifiers for one person, and two of one sector the same.

Until now every `sub` Hodor wrote was the person's user identifier, and Hodor read it back as one: UserInfo found the person by the access token's `sub`, token exchange found the person of a subject token by its `sub`, and logout initiated by the relying party compared the `sub` and `sid` of an `id_token_hint` with the browser's session. A person's identifier leaves Hodor in the ID token, the access token, UserInfo, introspection, the token made by an exchange and the logout token of back-channel logout. Access tokens are JSON Web Tokens: whoever holds one can read it, the client included. Every access token has a record in the register, which names the grant it was issued under, and the grant names the person. Roles, assignments, the Authorization API, audit events and webhooks all name a person by the user identifier.

Six questions had to be answered:

1. Which clients may be pairwise, and what their sector is.
2. How the identifier is computed, and from what secret.
3. Which tokens and answers carry it.
4. How Hodor finds the person when a token that names them by a pairwise identifier comes back.
5. What `sub` a token exchange gives when the subject token came from a pairwise client.
6. Whether anything but `sub` must change.

## Decision

- **A client has a subject type, `public` or `pairwise`, `public` unless chosen.** Only a client with `authorization_code` may be pairwise: only it signs people in. A client of client credentials, and so one bound to a workload, names itself or its workload, never a person, and stays public.
- **The sector is a host.** It is the host of the client's sector identifier address when it has one; otherwise the one host of its redirect addresses. A pairwise client whose redirect addresses name more than one host, or one without a host (a private-use scheme), must have a sector identifier address, as Core section 8.1 says. The port and the path are not part of the sector, and the host is compared in lowercase.
- **The sector identifier address is fetched when it is set, and only then.** When a pairwise client is created with one, or its address, its redirect addresses or its subject type change, the address is checked through the kernel's `DestinationCheck` and fetched with `GET` through the guarded outbound client: HTTPS, a public address, 10 seconds, 64 kibibytes, no redirect followed. The answer must be a JSON array of strings holding every redirect address of the client ([OpenID Connect Registration, section 5](https://openid.net/specs/openid-connect-registration-1_0.html#SectorIdentifierValidation)). It is not fetched again later: the sector is its host, and the document only proves that whoever controls the host agreed to the client's addresses.
- **The identifier is an HMAC.** `sub` is the base64url, without padding, of HMAC-SHA-256 under the tenant's **pairwise secret** of a message that names its use, the tenant, the sector and the person: 43 characters, the same every time for one person and one sector, and telling nothing about the person without the secret. Core section 8.1 suggests a hash of the sector, the account and a secret salt; an HMAC is that construction done the way cryptographers recommend.
- **The pairwise secret is one per tenant, sealed, and never changed.** 32 random bytes, made the first time the tenant needs one, kept in `oauth.pairwise_secret` sealed by the tenant's secret box ([secrets at rest](../security/secrets-at-rest.md)) and sealed again with the others by `hodor-cli secrets reseal`. Tenants have different secrets, and the tenant is in the message besides, so one person's identifiers never agree across tenants. Changing the secret would change every pairwise identifier of the tenant at once, so it is never rotated; a secret that no longer opens makes the token endpoint fail with `server_error` rather than make a new one.
- **Everything the client is given names the person by the pairwise identifier**: the ID token, the access token, UserInfo, introspection of its access and refresh tokens, and the logout tokens of back-channel logout. The access token is included because the client can read it; a pairwise `sub` that the access token beside it gives away would protect nobody.
- **`sid` is pairwise too, for a pairwise client.** The session's identifier is the same for every client the person signed in to in it, so two clients that compare the `sid` of their ID tokens could tell that they share a person. A pairwise client's `sid` is the HMAC of the session's identifier for its sector, computed as `sub` is with another use named; its ID tokens and logout tokens carry the same value.
- **A token that comes back is read through its record, never through its `sub`.** The register already names the grant of every access token issued for a person, a token made by exchange included, and the grant names the person. UserInfo and token exchange find the person there; a token without a grant is about no person. The `sub` they answer with is the one the token carries, so they agree with the ID token by construction.
- **Token exchange keeps the subject token's `sub`.** The person is the person of the subject token's grant, who must still be allowed to sign in; the new token's `sub` is the subject token's `sub`, whatever the agent's client is. The agent and the audience learn no more about the person than the client the person gave the token to; a token exchanged from a public client's token carries the user identifier, as before.
- **An `id_token_hint` is compared with what the hint's client was told.** At the end-session endpoint the hint's `sub` and `sid` are compared with the pairwise identifiers of the browser's session's person and session for the hint's client, and with the user and session identifiers for a public client.
- **Inside Hodor nothing changes.** Grants, consents, refresh token families, deliveries of logout tokens, roles and their assignments, the Authorization API, audit events and webhooks keep the user identifier. Audit events of token issuance and exchange keep naming the person by it, so an administrator can follow a person whatever their clients see.
- **Discovery says `subject_types_supported` `["public", "pairwise"]`.**

## Consequences

- A person's identifier at a pairwise client changes if the client's sector changes: a new sector identifier address with another host, redirect addresses of another host, or a switch of subject type. The administration interface and the context page say so; an application that moves to another host keeps its identifiers by naming a sector identifier address on the old host.
- Clients of one host share a sector, and so share identifiers. That is what a sector is for, and it is why two clients with redirect addresses only at `127.0.0.1` get the same identifiers: such a client names a sector identifier address of its own if it wants one.
- Resource servers see, in an access token issued to a pairwise client, the identifier of that client's sector. A resource server that serves clients of several sectors sees one person under several identifiers, and the Authorization API, which names people by their user identifier, knows none of them. A tenant whose resource servers decide about people through the Authorization API keeps the clients whose tokens reach them public.
- Pairwise identifiers stop `sub` and `sid` from being compared. Claims the person lets an application read, such as an email address or `groups`, still let two applications that both read them tell that they share a person; OpenID Connect leaves that to consent and to which claims a client may ask for.
- Issuing a token for a pairwise client reads and opens the tenant's pairwise secret, one row and one opening, in the server and, for logout tokens, in the worker.
- An address that served the sector identifier document when the client was saved may later serve something else; nothing is checked again, as nothing about it is used but its host.
- The suite's own pairwise tests, `oidcc-registration-sector-uri` and `oidcc-registration-sector-bad`, are of the Dynamic OpenID Provider plan and register their client dynamically, which Hodor does not offer. The conformance job runs the Basic and Back-Channel plans a second time with pairwise clients instead, where the suite checks that UserInfo, a second sign-in and the logout token give the `sub` and `sid` of the ID token ([OpenID conformance](../operations/conformance.md)).

## Alternatives considered

- **Pairwise identifiers in the ID token and at UserInfo only, the access token keeping the user identifier.** What several providers do with opaque access tokens; resource servers and the Authorization API would see the user identifier. Set aside: Hodor's access tokens are JSON Web Tokens the client can read, so the client would learn the user identifier from the first access token it got.
- **Encrypting the access token, or making it opaque, for pairwise clients.** It would let the access token carry the user identifier for resource servers alone. Set aside for now: opaque access tokens are a later epic ([the epics](../product/epics.md#later-epics-at-story-level)), and encryption would change what every resource server has to do.
- **A table of the pairwise identifiers issued, to find a person by one.** It would let the Authorization API, introspection or a resource server turn a pairwise identifier back into a person. Set aside: the register already finds the person of every token Hodor issued, and a lookup open to resource servers would undo, for whoever may ask, what the identifier hides.
- **A hash of the sector, the person and a salt, as Core section 8.1 writes it.** The same idea; set aside for the HMAC, which is the construction made for keyed hashing and costs the same.
- **A secret derived from the root keys instead of one stored.** Nothing to store. Set aside: identifiers would change whenever the root keys are rotated, and the root keys are meant to rotate.
- **Re-fetching the sector identifier document at every sign-in.** Set aside: the sector is the host, which the document cannot change; fetching it at sign-in would put an outside server in the path of every person signing in, and make an outage there stop them.
- **Keeping `sid` the session's identifier.** Simpler; set aside because it defeats the pairwise `sub` for as long as the session lasts.
- **Giving the exchanged token the pairwise identifier of the agent's client.** An agent's client has no redirect addresses and no sector, and the subject token's audience would then see a person it already knew under a new name.
