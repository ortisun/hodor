# Decision 0027: 0.3.0 holds operations, groups and organizations, workloads, and what 0.2.0 left out

Status: Accepted (requested by the project owner)

## Context

0.2.0 was released with Milestones 1 to 5: people sign in to a tenant with a password, an external identity, a second factor or a passkey; applications sign them in through OAuth and OpenID Connect; and applications ask Hodor whether someone may do something. [Decision 0023](0023-what-0.2.0-holds.md) cut each part to what makes it whole and left the rest to its phase.

After the release, the project owner asked for four more parts:

- **Running Hodor for real.** The gaps the [progress](../product/progress.md#known-gaps-in-what-is-done) page lists before any deployment: everyone behind a load balancer shares one limit on sign-in attempts, expired rows are never removed, continuous integration actions are pinned by tag, and the image and the chart are built only from a checkout.
- **Groups, organizations and SCIM.** Groups (Requirement-Identity-05) and organizations (Requirement-Identity-06) belong to Phase 1 and were never built, so roles cannot be given to them. SCIM (Requirement-SCIM-01, Phase 6) lets another system provision users and groups.
- **Workloads, agents and webhooks.** Service accounts and agents with their own credentials (Requirement-Workload-01), API keys (Requirement-Credential-06), delegation through token exchange with an actor chain (Requirement-Workload-02, Requirement-OAuth-16), and signed webhooks (Requirement-Audit-04). The parts of Phase 5 that Decision 0023 left out.
- **What 0.2.0 left out of Phases 2, 4 and 5.** Pairwise subject identifiers (Requirement-OAuth-10), claim mappers per client (Requirement-OAuth-21), back-channel logout (Requirement-OAuth-11), magic links and one-time passwords by email (Requirement-Authentication-05), and per-resource access control lists (Requirement-Authorization-04).

## Decision

- **0.3.0 is four milestones, built in this order:**
  1. [Milestone 6](../product/epics.md#milestone-6-hodor-runs-behind-a-load-balancer-and-cleans-up-after-itself), operations.
  2. [Milestone 7](../product/epics.md#milestone-7-groups-organizations-and-scim), groups, organizations and SCIM.
  3. [Milestone 8](../product/epics.md#milestone-8-workloads-agents-and-webhooks), workloads, agents and webhooks.
  4. [Milestone 9](../product/epics.md#milestone-9-what-020-left-out), what 0.2.0 left out.
- **The order follows what each part needs.**
  - Operations come first because every later part adds limits, tables and rows that must be cleaned up, and because the forwarded client address changes what every limit counts.
  - Groups come before workloads and before what 0.2.0 left out, because a claim mapper can map membership into a token, an access control list can name a group, and a webhook can announce what SCIM changed.
  - Workloads come before the deferred parts of Phase 2 because token exchange changes what a token's subject is, which pairwise identifiers and claim mappers have to account for.
- **Milestone 6 is what stands between 0.2.0 and a deployment behind a load balancer:** the client address forwarded by trusted proxies, one cleanup job for every kind of expired row, actions pinned by commit, licenses of the pages' dependencies checked, and the image and the chart published with each release. The limit on sign-ins started from one network that pull request #54 proposed is not in it. Its cause, a SAML response kept unverified, was fixed where it arrives.
- **Milestone 7 builds groups and organizations as [Decision 0005](0005-tenant-and-organization.md) describes them**, inside a tenant and in the identity context. Roles can then be assigned to groups and scoped to an organization, and a token can carry the organization a person chose. SCIM is a server for Users and Groups, called by a client of the tenant with an access token.
- **Milestone 8 adds principals that are not people.** Service accounts and agents are principals of the tenant. They hold clients and API keys. They are assigned roles like users. Token exchange issues a token for a subject on behalf of an actor and records the chain in `act`. Webhooks deliver the events of the outbox to endpoints a tenant registers, signed, retried and set aside when they keep failing.
- **Milestone 9 takes what Decision 0023 set aside for 0.2.0, and nothing more of those phases.** In:
  - pairwise subject identifiers;
  - claim mappers per client;
  - back-channel logout;
  - one-time passwords and magic links by email;
  - per-resource access control lists in the native engine.

  Out:
  - one-time passwords by text message, which need a provider Hodor does not have;
  - HOTP;
  - front-channel logout;
  - relationship-based access control;
  - rich authorization requests;
  - the JWT bearer grant;
  - export to a security event management system.
- **0.3.0 is released when Milestone 9 is done**, following [the release rules](../development/conventions.md#releases).
- **The rules of the project stay.** The documentation of each issue comes first. Cross-tenant cases cover every new token, credential, code and table. Each milestone ends with a demonstration that runs in continuous integration.

## Consequences

- At 0.3.0 Hodor can be deployed behind a load balancer, a business customer's directory can provision its people into a tenant, and a service or an agent can act on its own or on a person's behalf.
- 0.3.0 is still not general availability. High availability, a disaster recovery drill, an external pentest and the external review of SAML stay in Phase 9, and the changelog says so.
- What is left out is not dropped. It keeps its phase, and the roadmap's phases keep their numbers.
- Groups and organizations change the identity context, which every earlier milestone reads. Their issues extend the cross-tenant suite and the contract suites of that context before anything else uses them.
- Publishing the image and the chart makes their names public: a published image can be pulled and run by anyone who has the address. Neither holds a secret ([Decision 0022](0022-installation-packages.md)).

## Alternatives considered

- **A release after each milestone.** It is possible, and nothing in the plan prevents it. Set aside because the owner asked for the four parts together.
- **Workloads before groups.** Service accounts do not need groups. Set aside because claim mappers, access control lists and webhooks would then be built before the membership they act on exists.
- **Operations last, with Phase 9.** Set aside because the forwarded address and the cleanup job are needed by the first deployment, which should not wait for general availability.
